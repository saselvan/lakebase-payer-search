# Rank Payers from shared Search texts, not from Search keys

ADR 0003 stopped one Payer's copies from filling the candidates; the same failure came back across Payers. On production, 48,283 Search keys hold only 22,417 Search texts, and 44 texts are shared by more than 100 Payers each, so for `uhc` the 100 nearest Search keys were all the text "uhc" and none belonged to a UnitedHealthcare-named Payer. We find candidates by Search text, expand each text to every Payer that has it, and give each Payer the Relevance of its best text. Payers of equal Relevance are ordered by Own-name match (any of the Payer's Own-name texts, not only the one it was found by), then by Specificity (fewer Payers share the text), then name, then `payer_id`. We rejected removing the shared Aliases (a former company name truly belongs to every Payer of that company, and a cloner's own data will have them) and a larger candidate cut (any fixed cut fails once one text is shared by more Payers than the cut).

Own name and Specificity order ties only; they do not change Relevance. We first built them as score weights (an Own-name bonus, and a text score divided by a function of its Payer count). On the branch eval against the production function, every weight tried lost queries that the old search found (6 to 23 per run); as tie-breaks, no query left the top 10. Five queries left the top 50 (old ranks 28 to 41): the text cut now reaches all Payers of a widely shared text that score above the right Payer, where the old key cut stopped part-way through them. BM25 stays on the Search keys, whose documents hold the Payer's state word, and its cut takes each text's best key score: a per-text document without the state lost "ny bcbs" and "md blue cross" in the same eval.
