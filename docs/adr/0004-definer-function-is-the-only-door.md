# The Caller can only execute two functions; a definer function owns all data access

The Data API runs every request as the Caller's own Postgres role, so whatever that role can read, the API can expose. We give the Caller EXECUTE on the public function `api.search_insurers` (in `api`, the only exposed schema) and on the core function `search_idx.search_core`, which the public function needs when it runs as the Caller, and nothing else: no SELECT on any table, no INSERT on the log. The public function passes the Caller's identity to the SECURITY DEFINER core function, owned by a NOLOGIN role, which alone reads the search keys and appends to the Search log. Because the Caller can also call the core function directly, a direct login could pass any caller text; the core function therefore records `session_user` on any login other than `authenticator`, which the Caller cannot become. A leaked token can search payers, and nothing more. Trade-off: the search writes a log row, so it cannot run on a read-only replica.
