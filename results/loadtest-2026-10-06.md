# Load test, 2026-10-06: insurer search over the Lakebase Data API

## Method
- **Where:** load generated **in-region** (AWS us-east-1, same region as the Lakebase endpoint) from serverless
  job tasks, so the numbers are the API path, not a laptop's network. 4 parallel tasks x 1 Locust process
  (4 CPUs each; Locust never warned about generator CPU). Locust 2.46.6, `FastHttpUser`, Python 3.12.
- **Path:** `POST <data-api>/api/rpc/search_insurers` with a service-principal OAuth token (M2M), exactly as the
  EHR backend would call it. Every request runs the full search (trigram + BM25, one row per payer) and writes
  one Search log row.
- **Load:** closed loop, **no think time** (each user sends the next request as soon as the last returns).
  Steps 10 / 25 / 50 / 100 / 200 / 400 users, 60 s each, first 10 s of each step excluded.
- **Query mix:** 34 realistic payer queries; 80 % page 1, 20 % pages 2-5; **30 % get one random typo**;
  500 rotating Tenants (`customer_id`).
- **Data:** 3,000,000 alias rows (6,291 payers) synced from Unity Catalog; search over 33,203 normalised keys.
- **Database:** Lakebase Autoscaling endpoint, CU range 2-16 (not changed during the test).
- **Totals across tasks:** rps and requests add up; p50 = median of task p50s; p95/p99 = worst task (conservative).

## The ceiling and the bottleneck
- **Throughput ceiling: about 200-245 requests/s, reached at about 25 concurrent no-think-time users.**
  More users only add queueing: latency grows linearly, throughput stays flat.
- **No errors at any step:** 0 failures in about 77,000 requests, up to 400 users and 211 open Postgres connections.
  No 429, no 5xx, no "Too many connections" (the July 2026 incident pattern did not appear).
- **The limit is database CPU, not the API gateway.** Evidence, sampled every ~18 s during the run:
  - `num_cpus()` = **4** for the whole run (the endpoint was at its 16 CU ceiling: about 4 vCPUs at 16 CU).
  - In-database search time (from `audit.search_log.duration_ms`) rose from **p50 20 ms / p95 50 ms** at low load
    to **p50 150 ms / p95 400 ms** at 100+ users, with 85-104 active backends: requests queue for CPU.
  - 4 CPUs / ~235 rps = **about 17 ms of CPU per search**. Searches per minute held flat at ~14,000 from 50 users up.
  - At 10 users the client p50 (36 ms) was ~16 ms above the in-database p50 (~20 ms): that is the gateway + network.
- **What this means for your application:** "thousands of requests a day" is far below this. 235 rps is ~20 M searches/day
  at a flat rate. With real users (think time of ~1 s between keystrokes/pages), ~200 concurrent users fit.

## How to raise the ceiling (not tested here)
1. Less CPU per search: smaller candidate sets (300 -> 100), no per-search log write (log asynchronously), or a
   prefix/typeahead cache for the most common queries.
2. Read replicas: add read-only endpoints and spread traffic. Today the search writes a Search log row, so it must
   run on the read-write endpoint (ADR 0004); moving the log write elsewhere unlocks replicas.
3. A bigger compute raises vCPUs only in steps (about 1 vCPU per 4 CU in our earlier measurements).

## Caveats (honest)
- **AWS, not Azure.** Same Lakebase API and Data API; Azure numbers need their own run.
- One test, one day. Other light traffic (functional tests) ran on the same endpoint during part of the window.
- Load came from 4 serverless tasks in one region; in production, your calling application's network path may add additional latency.
- Closed loop with no think time is a stress shape, not a user shape. Laptop numbers in other notes include
  ~115 ms of network per request and are labelled as such.
