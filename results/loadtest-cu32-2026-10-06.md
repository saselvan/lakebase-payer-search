# Load test, 2026-10-06: 16–32 CU

**Result: about 440–465 requests/s with 0 failures** (16 CU run: about 200–245). Same API, same data.

Method: a throwaway branch of production (4 h TTL, deleted after), endpoint set to 16–32 CU before the
run, Data API inherited by the branch (one search checked first: 200, right top hit). Load: 8 parallel
serverless Locust tasks in the same region, 60 s per step, no think time, 30% typo queries, same
locustfile as the 16 CU run. `DATA_API_BASE=<branch base> uv run python scripts/run_loadtest.py --tasks 8 --steps 25,50,100,200,400,800 --name cu32b`

- Ceiling reached at about 25–50 users; above that only wait time grows. 0 failures at 800 users.
- Throughput about doubled from 16 CU, which fits CPU doubling (about 1 vCPU per 4 CU).
- 32 CU is the autoscaling maximum, so this is the single-endpoint ceiling for this search function.

## A failed earlier attempt (kept for the lesson)
A first branch ran at **1 CU** by mistake (a new branch starts at the project default). It held about
55 requests/s, then at 200+ users returned **HTTP 500 "out of memory"** for most requests. Lesson: an
undersized compute under a burst fails, it does not only slow down. Set the minimum CU for normal peak.

## Caveats
- The script's DB sampler reads production, not the branch, so no DB-side numbers for this run.
- AWS, not Azure. Load came from one region; in production, your calling application's network path may add additional latency.
