## Q1. What are you trying to do?
Owner: "The objective is to show Lakebase Search, along with Data API as the mechanism with security rules."
Show three things working together: Lakebase Search (typo-tolerant ranking inside Postgres), the Data API as the way in, and the security rules that guard it. The vehicle is a clean insurer finder that a front-desk or call-center person would use: type a messy name such as `bcbs ga` and get the right plan.

## Q2. How is it done today, and what are the limits? (approved draft)
Teams usually add a separate search engine next to their database, plus an app server that holds database credentials and checks permissions in app code. That means a second system to keep in sync, a sync job to watch, and a security model spread across app code and the database. (Neutral: no vendor named or criticized.)

## Q3. What is new, and why will it succeed?

### Non-negotiables (approved, 2026-10-23)
1. Every result on screen comes from a live call to `api.search_insurers`. No mock data, no cached results. (Prevents: a demo that lies.)
2. The browser never holds a credential. The app server calls the Data API with the app's own service principal OAuth token. No Postgres password anywhere. (Prevents: decorative security.)
3. The app's service principal gets only the Caller grants: EXECUTE on the two functions, no table rights. The lens shows them read live from the catalog, not typed text.
4. Every number on screen is measured live, or it carries its source and date. (Prevents: made-up speeds.)
5. The lens shows the real request and the real response, with the token hidden.
6. Example typos come from the shared top-hit list that the live tests check.
7. Front door: no jargon. Expert drawer closed by default (3-surface rule).
8. No customer names. The screen says plainly that the IDs are synthetic and the payer names are public.
