# Telemetry and tracing module: plan (no build)

**Date:** 2026-10-23 · **Status:** plan only. No code, no commits, no production writes.
**Protects:** every timing and "what ran" claim in the app, deck and video; the DBA/security skeptic's ability to trace one search from the browser to the Postgres statement.
**Must never happen:** a timing with no traceable source · a trace or log carrying the OAuth token, the client secret, or query text beyond what `audit.search_log` already stores · a claim about a Databricks product's tracing support without grade 1-3 evidence (grade 1 = a check run, 2 = code/schema read, 3 = official docs with URL and date; Glean, blogs and AI output are leads, marked UNPROVEN).

## 1. Raw sources (what each actually holds)

Request path (grade 2, `server/main.py`, `server/dataapi.py`): browser → finder app server `POST /api/search` → `POST {DATA_API_BASE}/api/rpc/search_insurers` with `Authorization: Bearer` (app SP) → Data API generated statement → `api.search_insurers` (SECURITY INVOKER) → `search_idx.search_core` (SECURITY DEFINER) → `INSERT audit.search_log`.

**Data API response headers** (grade 1, branch `t-telem-1023a`, 2 searches, 2026-10-23 21:10Z):
- `server-timing: request_id;dur=0;desc="<uuid>", client_protocol;dur=0;desc="HTTP/1.1"`. Durations are 0. It carries no DB or Data API timing.
- `x-request-id` is generated by the Data API. A client-sent `x-request-id: telem-probe-1` was ignored. The Server-Timing `desc` equals `x-request-id`.
- `neon-request-id` is also returned.
- No `traceparent` is echoed.

**pg_stat_statements** (grade 1 on branch, grade 3 for docs):
- Preloaded in `shared_preload_libraries` but NOT installed in the database. Branch copy of production had no extension. `CREATE EXTENSION` on the branch worked (v1.11).
- The statement the Data API ran is a generated CTE: `subzero_payload`, `subzero_body`, `subzero_args`, `subzero_source`, `_subzero_query`. It calls `"api"."search_insurers"("q" := (select …), "customer_id" := …, "lim" := …, "off" := …)`. The request values are bound parameters (`$1` … `$16`), so the statement text holds no literal `q`. Length 1,066 chars.
- A search with `traceparent: 00-4bf92f…` did NOT put the trace id into the statement text (0 matches).
- Per-execution data is not available: pg_stat_statements is aggregated by normalized text.

**audit.search_log** (grade 2 DDL in `sql/10_search_index.sql:193`; grade 1 rows):
- Columns: `search_id`, `searched_at`, `customer_id` (Tenant), `caller`, `q`, `lim`, `off`, `result_count`, `duration_ms`. There is no trace column.
- `caller` = `current_user` inside `api.search_insurers`. On a call through the Data API it was the Caller SP id (grade 1).
- `q` stored = the normalized query (trimmed, lower-cased, whitespace-collapsed) at `sql/20:157`.
- `duration_ms` = `clock_timestamp()` at the start of `search_core` to the insert. It is in-function time only. It excludes the HTTP hop, auth and the Data API. Observed 13.35 and 13.20 ms for two calls. 152 rows on the branch before the test.

**EXPLAIN (ANALYZE, BUFFERS)** (grade 1, `api.search_insurers('bcbs ga','<tenant:masked>',10,0)`):
- One node, `Function Scan on search_insurers`, actual 20.78 ms, `shared hit=7232`, Execution Time 20.86 ms.
- PL/pgSQL inner statements are NOT shown. A plan view of the search needs `auto_explain` or pg_stat_statements. `auto_explain` is preloaded (lead: it logs plans and may log query text, which goes beyond the audit boundary).

**App logs** (grade 1): `databricks apps logs lakebase-payer-finder` returned one line, `Starting Databricks Apps runtime…`. The server logs only failure paths (status and SQLSTATE; never the body or token, `dataapi.py`). There is no per-request log today.

**Not proven (blocked):** whether the Data API passes request headers (`traceparent`) into SQL as a GUC (`request.headers` or similar). A probe function (`api.telem_probe`, branch only) was denied by the auto-mode classifier ("Credential Materialization"). It was not retried or routed around. It was never created: a read-only check shows `api` holds only `search_insurers`. The question stays open for Samuel (see §6).

| OTel GenAI agent/tool spans | Tool span `execute_tool {gen_ai.tool.name}`, kind INTERNAL, `gen_ai.tool.name` required; `gen_ai.tool.call.arguments` and `.result` opt-in and sensitive; status Development. | https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-spans.md · 2026-10-23 |
| W3C trace context | `traceparent` = `version-trace_id(32 hex)-parent_id(16 hex)-flags`. | https://www.w3.org/TR/trace-context/ · 2026-10-23 |
| sqlcommenter | Adds `/*traceparent='…'*/` as a SQL comment; visible in DB statement logs, not in pg_stat_statements per execution. | https://google.github.io/sqlcommenter/ · 2026-10-23 |
| pg_tracing (DataDog, early dev) | Server-side spans; takes traceparent from a sqlcommenter comment or the `pg_tracing.trace_context` setting; needs shared_preload + restart. | https://github.com/DataDog/pg_tracing · 2026-10-23 |
| pg_stat_statements | Normalized text; representative query; cumulative since reset. | https://www.postgresql.org/docs/current/pgstatstatements.html · 2026-10-23 |

| Neon / Supabase | Neon's query view is pg_stat_statements; stats are not kept across scale-to-zero. Supabase counters are cumulative since reset. | https://neon.com/docs/introduction/monitor-query-performance · https://supabase.com/docs/guides/observability/inspect · 2026-10-23 |

**Security angle (from the survey):** attribute the call to a service identity (here the Caller SP id, already in audit); keep parameter values out of spans (opt-in in OTel); keep tool arguments opt-in; never place the Authorization header in spans; and test for absence, not only for presence.

## 3. Trace design (proposed; not built)

**Recommended trace:** one trace per search, created by the app server.
```
SERVER  POST /api/search              (FastAPI instrumentation; root; trace id minted here)
 ├─ CLIENT POST /api/rpc/search_insurers  (httpx instrumentation; injects traceparent)
 │    └─ [outside the trace] Data API → SQL → search_core → audit row
 └─ (token refresh span, only when it happens)
```
- The Data API is a black box to OTel. Database time comes from `audit.search_log.duration_ms` (in-function), not from a span. The span must NOT claim more than that.
- Span attributes: `db.system.name=postgresql`, `db.operation.name=SELECT`, `db.query.summary=search_insurers`, `server.address` (host only). Do NOT put `q`, the bound arguments, the token or the Authorization header in spans. `q` is already in audit; the span stays a pointer, not a copy.
- Sampling: `always_on` (the Databricks Apps docs say so; see §4).

**The join id into Postgres: options and trade-offs**

| Option | How | Trade-off | Status |
|---|---|---|---|
| A. SQL comment (sqlcommenter style) | Data API adds a comment to its generated statement | The app cannot inject SQL through the RPC; the generated statement had no comment | Not available unless Databricks changes the Data API |
| B. Request header → GUC | Data API exposes `traceparent` as a GUC; `search_core` reads it and writes it to audit | Zero schema change if it works; depends on an undocumented Data API behaviour | UNPROVEN (probe denied) |
| C. Explicit id argument + audit column | App mints `trace_id` (32 hex) and passes it as a new argument to `api.search_insurers`; `search_core` stores it in a new `audit.search_log.trace_id` | Schema change (`sql/10`), function signature change (`sql/20`, lens `arguments`), grants re-check (`sql/40`, `test_app_sp_grants`). Deterministic; works regardless of B | Recommended unless B is proven |
| D. pg_stat_statements | Match by `queryid` and time window | Aggregate only; cannot tie one request to one statement. Use as a counter check, not a join | Use as a counter delta (+1 per search on a quiet branch) |

**Recommended join:** C for the per-request key (app span ↔ audit row). The app records the Data API `x-request-id` as a span attribute (the Data API's own id for the call, grade 1) so the Data API side is linked too. D verifies the statement shape and counts. B is added only if the probe proves it.

**Transport:** OTel SDK, `opentelemetry-instrumentation-fastapi`, `opentelemetry-instrumentation-httpx`, OTLP exporter. Local test: Jaeger with OTLP. In Databricks Apps: platform export to UC tables `otel_spans`, `otel_logs`, `otel_metrics` (see §4); external OTLP is NOT confirmed.

## 6. Outside checks for the later build

1. **Join:** one live search returns a trace id; the same id appears in the Jaeger trace (app span attribute), the `audit.search_log` row (M1), and the Data API `x-request-id` span attribute.
2. **Counter:** `pg_stat_statements` `calls` for the `search_insurers` statement rises by exactly 1 across the test window (quiet branch), and `mean_exec_time` is in line with audit `duration_ms`.
3. **Nesting:** app span ≥ HTTP client span ≥ audit `duration_ms`.
4. **Mutation:** dropping the id argument turns the join test red (in the lens and the audit column).
5. **Absence:** no span, log, or lens text contains the bearer token, the client secret, or the Authorization header. Red under a mutation that adds them.
6. **LakeWatch:** only if E12/E13 are proven; otherwise the check is out of scope.
